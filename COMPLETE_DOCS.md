**Why folder-based routing:** In the Next.js App Router, a folder under `app/` maps to a URL segment, and special filenames carry meaning: `page.tsx` = the route's UI, `layout.tsx` = a wrapper shared by nested routes, `route.ts` = an API endpoint, `loading.tsx` = a Suspense fallback, `error.tsx` = an error boundary, `not-found.tsx` = the 404 page. This removes the need for a central router config.

## 3. DATABASE — `prisma/schema.prisma`

**Generator:** `provider = "prisma-client"`, `output = "../app/generated/prisma"` (client code is generated into the app folder).
**Datasource:** `provider = "postgresql"` (URL injected at runtime).

**Conventions used by every feature model:** primary key `id String @id @default(cuid())` (collision-resistant random IDs); a `userId String` foreign key; a relation `user User @relation(fields: [userId], references: [id], onDelete: Cascade)` (deleting a user deletes all their rows); timestamps via `@default(now())`.

### `prisma.config.ts` — every setting
```ts
import dotenv from "dotenv";
dotenv.config({ path: ".env.local" });       // load env for the Prisma CLI
import { defineConfig } from "prisma/config";

function withPoolingHints(url?) {              // append pgbouncer hints if missing
  if (!url) return url;
  if (url.includes("pgbouncer")) return url;
  const sep = url.includes("?") ? "&" : "?";
  return `${url}${sep}pgbouncer=true&connection_limit=1`;
}

export default defineConfig({
  schema: "prisma/schema.prisma",             // schema location
  migrations: { path: "prisma/migrations" },  // migrations folder
  datasource: { url: withPoolingHints(process.env["DATABASE_URL"]) },
});
```
- **`dotenv.config({ path: ".env.local" })`** — Prisma CLI doesn't auto-load `.env.local`, so it's loaded explicitly.
- **`withPoolingHints`** — appends `pgbouncer=true&connection_limit=1` so the Prisma CLI behaves correctly behind Supabase's connection pooler (disables prepared statements; caps connections). Idempotent.
- This file configures the **CLI** (migrate/db push/studio), not the runtime client.

### `lib/prisma.ts` — the singleton (line by line)
```ts
import { PrismaClient } from "@/app/generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined };
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
export const prisma = globalForPrisma.prisma ?? new PrismaClient({ adapter });
if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
```
- **Line 1–2:** import the generated client and the `pg` driver adapter.
- **Line 4:** cast `globalThis` to a typed object holding an optional `prisma` (so we can stash the client globally).
- **Line 6:** create a `PrismaPg` adapter wrapping a node-postgres connection using `DATABASE_URL`.
- **Line 8:** export `prisma` = the cached instance if present, otherwise a new `PrismaClient`.
- **Line 9:** in non-production, cache it on `globalThis` so hot-reload doesn't spawn new clients (and exhaust DB connections). **Why:** without this, dev hot-reload would create dozens of pools.

### `lib/auth.ts` — NextAuth config
```ts
export const authOptions: NextAuthOptions = {
  adapter: PrismaAdapter(prisma as never) as NextAuthOptions["adapter"],
  providers: [ GoogleProvider({ clientId: process.env.GOOGLE_CLIENT_ID!, clientSecret: process.env.GOOGLE_CLIENT_SECRET! }) ],
  session: { strategy: "database" },
  pages: { signIn: "/login" },
};
```
- **`adapter: PrismaAdapter(prisma)`** — persists `User`/`Account`/`Session`/`VerificationToken` in our DB. (The `as never`/`as ...` casts reconcile Prisma 7 types with the adapter's expected types.)
- **`providers`** — one `GoogleProvider` reading `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (the `!` asserts they're defined).
- **`session.strategy: "database"`** — sessions are stored as DB rows; the browser holds only an opaque `sessionToken` cookie.
- **`pages.signIn: "/login"`** — use our custom login page instead of NextAuth's default.

### `lib/dashboard.ts` — full reference
**Exports:**
- `type ModuleKey` = `"finance"|"fitness"|"mind"|"business"|"discipline"|"people"`.
- `interface ModuleResult` = `{ key: ModuleKey; score: number | null; status: string }`.
- `interface TrendPoint` = `{ label: string; score: number | null }`.
- `interface DashboardData` = `{ lifeScore: number; modules: Record<ModuleKey, ModuleResult>; trend: TrendPoint[]; brief: string }`.
- `async function getDashboardData(email: string): Promise<DashboardData>`.

**Internal helpers:**
- `clamp(n)` → `Math.max(0, Math.min(100, Math.round(n)))`.
- `avg(nums)` → mean, or 0 for empty.
- `startOfDay(d)`, `addDays(d, n)`, `dayKey(d)` (`"Y-M-D"` string).
- `interface RawData` — typed shape of all fetched rows.
- `safeQuery<T>(fn)` — runs a Prisma query in try/catch; returns `[]` on failure (logs `"Dashboard query failed:"`).
- `computeModules(raw, ref)` — computes all 6 `ModuleResult`s as of reference day `ref`.
- `scoresOf(modules)` — array of non-null scores.
- `lifeScoreFrom(modules)` — `clamp(avg(scoresOf))` or 0.
- `scoreFinance`, `scoreFitness`, `scoreMind`, `scoreBusiness`, `scoreDiscipline`, `scorePeople` — per-module scorers (math in §10).
- `LABELS` — `ModuleKey` → display label.
- `buildBrief(modules, lifeScore)` — the daily brief text.
- `smartTip(worst, hour)` — one tip tailored to weakest module + time of day.
- `safeDefault()` — returns a zeroed `DashboardData` with brief `"Welcome to LifeOS. Start logging your data!"`.

**`getDashboardData(email)` flow:**
1. Wrapped in try/catch (returns `safeDefault()` + logs `"Dashboard data error:"` on failure).
2. If `!email` → `safeDefault()`.
3. Look up user by email (`select: { id: true }`); if none → `safeDefault()`.
4. `today = startOfDay(now)`; `since = addDays(today, -40)` (fetch window).
5. `Promise.all` of 11 `safeQuery` calls fetching transactions, workouts, sleepLogs, medLogs, journal, habits, checkIns, goals, tasks, interactions, contacts (date-windowed where applicable; `habits/goals/tasks/contacts` fetched fully).
6. Build `raw` (each `?? []`).
7. `modules = computeModules(raw, today)`; `lifeScore = lifeScoreFrom(modules)`.
8. Build `trend`: loop `i = 6 → 0`, `day = addDays(today, -i)`, compute that day's modules and life score; label via `toLocaleDateString("en-US", { weekday: "short", day: "numeric" })` → e.g. `"Mon 26"`; score `null` if no modules tracked that day.
9. Return `{ lifeScore, modules, trend, brief: buildBrief(modules, lifeScore) }`.

<a name="5-authentication"></a>
## 5. AUTHENTICATION (NextAuth + Google OAuth)

### `app/api/auth/[...nextauth]/route.ts`
```ts
import NextAuth from "next-auth";
import { authOptions } from "@/lib/auth";
const handler = NextAuth(authOptions);
export { handler as GET, handler as POST };
```
A **catch-all** route (`[...nextauth]`) handling every NextAuth endpoint (`/api/auth/signin`, `/callback/google`, `/session`, `/signout`, `/csrf`, `/providers`). Both `GET` and `POST` map to the same handler.

### Session strategy
Because `session.strategy === "database"`:
- A successful login creates a `Session` row and sets a `sessionToken` cookie (opaque, not a JWT).
- `getServerSession(authOptions)` reads the cookie, looks up the `Session` row, and returns the `User`.
- **JWT contrast:** with `strategy: "jwt"` the session would live entirely in a signed cookie (no DB read). This app uses DB sessions because the Prisma adapter is configured and instant revocation/audit is desirable.

### Protected routes
- `app/dashboard/layout.tsx` calls `getServerSession`; `null` → `redirect("/login")`. All `/dashboard/*` pages are nested inside it, so the guard runs before any of them render.
- Every API route independently re-checks the session (never trusts the client).

### `NEXTAUTH_SECRET`
Used by NextAuth to sign/encrypt the session-token cookie, the CSRF token, and the OAuth `state` parameter. Without it (or if leaked), cookies could be forged.

<a name="6-api-routes"></a>
## 6. API ROUTES (REST)

**REST recap:** resources are addressed by URL; HTTP verbs act on them — `GET` (read), `POST` (create), `PATCH` (partial update), `DELETE` (remove). Bodies/responses are JSON. Each `route.ts` exports functions named after the verb and runs as a serverless function.

### Shared `requireUserId()` helper (used by 20 routes)
```ts
async function requireUserId() {
  const session = await getServerSession(authOptions);
  if (!session?.user?.email) return null;
  const user = await prisma.user.findUnique({ where: { email: session.user.email }, select: { id: true } });
  return user?.id ?? null;
}
```
Returns the user's `id` or `null`. Callers return `401 {"error":"Unauthorized"}` when `null`. (Collapses "no session" and "no user row" into one 401.)

### Universal contracts
- **JSON parse failure** on POST/PATCH → `400 {"error":"Invalid JSON"}`.
- **Ownership:** mutations use `where: { id, userId }` via `updateMany`/`deleteMany`; a 0-row result → `404 {"error":"Not found"}`. PATCH re-reads via `findUnique` after a successful ownership-scoped update.
- **DELETE:** requires `?id=`; missing → `400 {"error":"Missing id"}`; success → `200 {"ok":true}`.
- **Dates:** optional `date` defaults to `new Date()`; invalid → `400 {"error":"Invalid date"}` (some routes: `"Invalid target date"`/`"Invalid due date"`).

### 6.1 `auth/[...nextauth]` — `/api/auth/*`
NextAuth handler (see §5). No Prisma/validation in the file.

### 6.2 Fitness

**`/api/fitness/workouts`** — model `Workout`.
- **GET:** `findMany({where:{userId},orderBy:{date:"desc"}})` → `200 {"workouts":[]}`; 401.
- **POST:** body `exercises[]` (required, non-empty; each `{name(req,string), sets(≥0 int), reps(≥0 int), weight(≥0)}`), `duration` (>0 int, req), `notes?` (string|null), `date?`. → `201 {"workout"}`. Errors: 401; 400 Invalid JSON / "At least one exercise is required" / "Exercise name is required" / "Invalid sets" / "Invalid reps" / "Invalid weight" / "Invalid duration" / "Invalid date".
- **DELETE:** `?id` → `deleteMany({id,userId})`. Standard contract.

<a name="9-ai"></a>
## 9. AI INTEGRATION — `app/api/ai/coach/route.ts`

- **Imports** `getDashboardData, DashboardData` from `@/lib/dashboard`. Reads `GEMINI_API_KEY`, `GEMINI_MODEL` (`const GEMINI_MODEL = process.env.GEMINI_MODEL || "gemini-2.5-flash"`).
- **`buildContext(data)`** formats `Overall Life Score`, each module's `score/100 — status`, and the 7-day trend list into text.
- **POST flow:**
  1. `getServerSession`; no email → `401 {"error":"Unauthorized"}`.
  2. No `GEMINI_API_KEY` → `200 { configured:false, answer:"...not connected..." }`.
  3. Parse `question` = `String(body?.question ?? "").trim().slice(0,1000)`; JSON error → `""`.
  4. Empty → `400 {"error":"Please ask a question."}`.
  5. `getDashboardData(email)` in try/catch; failure → `200 { answer:"Sorry, I couldn't read your data..." }`.
  6. POST to `https://generativelanguage.googleapis.com/v1beta/models/${GEMINI_MODEL}:generateContent?key=...` with `systemInstruction` (coach persona: "use ONLY this data", "do not invent numbers", "short, simple English"), `contents` (context + question), `generationConfig { temperature:0.6, maxOutputTokens:800, thinkingConfig:{ thinkingBudget:0 } }`.
  7. Non-OK Gemini → `200 { answer:"The AI had a problem answering...", error:true }`.
  8. Fetch throw → `200 { answer:"Sorry, something went wrong reaching the AI..." }`.
  9. Success → extract `candidates[0].content.parts[].text` joined → `200 { configured:true, answer }`.
- **Grounding (RAG-lite):** the user's real numbers are injected into the prompt, so answers are personal and the model is told not to fabricate.
- **`thinkingBudget:0`** disables the 2.5-flash model's internal "thinking" so the full token budget produces the visible answer.

<a name="10-scoring"></a>
## 10. DASHBOARD SCORING ALGORITHM (`lib/dashboard.ts`)

`clamp(n) = max(0, min(100, round(n)))`. Each module returns a score 0–100 or `null` (no data). Windows are relative to the reference day `ref`: `weekStart = ref-6 days`, `monthStart = ref-29 days`, `endEx = ref+1 day`.

### Finance (`scoreFinance`, rolling 30 days)
- Sum `income` and `expenses` from transactions in `[monthStart, endEx)`.
- If no transactions → `null`, status "No transactions in the last 30 days".
- If `income > 0`: `rate = (income - expenses) / income`; **`score = clamp(rate * 250)`** (i.e., 40% saved → 100; 20% → 50; ≤0% → 0); status `"{round(rate*100)}% of income saved (30 days)"`.
- Else (expenses only) → score `40`, status "Spending tracked — add income to score it".

### Fitness (`scoreFitness`, last 7 days)
- `workoutCount` in `[weekStart, endEx)`; `avgSleep` = mean hours of sleep logs in window.
- If no workouts and no sleep → `null`.
- `workoutScore = clamp(workoutCount / 4 * 100)` (4/week = full).
- If sleep present: `sleepScore = clamp(100 - |avgSleep - 7.5| * 20)` (7.5h ideal; each hour off −20).
- **`score = clamp(avg([workoutScore, sleepScore?]))`**; status `"{n} workout(s) this week, avg {h}h sleep"`.

### Mind (`scoreMind`, last 7 days + streak)
- `streak` = consecutive days up to `ref` with a meditation log.
- `medDaysThisWeek` = distinct meditation days in `[weekStart, endEx)`.
- `moodAvg` = mean journal `mood` (1–5) this week.
- If no meditation and no mood → `null`.
- `parts = [clamp(medDaysThisWeek/7*100)]`; if mood present add `clamp(moodAvg/5*100)`.
- **`score = clamp(avg(parts))`**; status = streak (`"{n}-day meditation streak"`) or mood or days-meditated.

### Business (`scoreBusiness`, current state)
- `activeGoals` = goals with `status==="active"`; `done`/`pending` from tasks (`done`/`completed`).
- If no goals and no tasks → `null`.
- `parts`: if active goals, `clamp(avg(progress))`; if tasks, `clamp(done/total*100)`.
- **`score = clamp(avg(parts))`**; status `"{p} task(s) pending, {g} active goal(s)"`.
- (Goals/tasks lack completion timestamps, so this component is constant across the historical trend.)

### Discipline (`scoreDiscipline`, last 7 days)
- If no habits → `null`.
- Per habit, `perHabit = frequency==="weekly" ? 1 : 7`; `expected += perHabit`; `actual += min(checkIns this week for habit, perHabit)`.
- `rate = actual/expected`; **`score = clamp(rate*100)`**; status `"{round(rate*100)}% of habits done this week"`.

### People (`scorePeople`, last 7/14/30 days)
- If no contacts → `null`.
- `interactions7` = interactions in `[weekStart, endEx)`.
- `overdue` = first high-priority contact with no interaction in the last 14 days.
- **`score = clamp(interactions7 / 3 * 100)`** (target ~3/week); status = "Reach out to {name} — overdue" or "{n} interaction(s) this week".

### Life Score
`lifeScoreFrom = clamp(avg(scoresOf(modules)))` — the **average of modules that have data** (`null` excluded); 0 if none.

### 7-day trend
For each day `ref = today-6 … today`, compute that day's modules using only data up to `ref`, then that day's life score; label = `"{weekday} {day}"`; `null` if nothing tracked that day.

### Daily brief (`buildBrief` + `smartTip`)
- No tracked modules → onboarding message.
- Else rank tracked modules; sentence 1 = Life Score band (≥75 "Strong", ≥50 "Steady", else "Tough"); sentence 2 = strongest module; sentence 3 = weakest module; sentence 4 = `smartTip(worst, hour)` — a concrete next step tailored to the weakest module **and time of day** (morning/evening variants for fitness/mind/discipline; uses the overdue name for people).

<a name="13-data-flow"></a>
## 13. COMPLETE DATA FLOW (example: adding an expense)

1. **User** fills the Add-transaction form in `FinanceClient.tsx` and clicks "Add transaction".
2. **`handleAddTransaction(e)`** validates `amount` (finite, > 0), then `fetch("/api/finance/transactions", { method:"POST", body: JSON.stringify({ amount, category, description, type, date }) })`.
3. **Browser → Vercel serverless function** `app/api/finance/transactions/route.ts → POST()`.
4. **Auth:** `getServerSession(authOptions)` reads the `sessionToken` cookie → looks up the `Session` and `User`. If no session → `401`; if email maps to no user → `404`.
5. **Validate:** parse JSON (`400 Invalid JSON` on failure), validate `amount`/`category`/`type`/`date`.
6. **Write:** `prisma.transaction.create({ data: { userId: user.id, amount, category, description, type, date } })`.
7. **Prisma → `PrismaPg` adapter → `pg` → Supabase PostgreSQL** executes an `INSERT`.
8. **Response:** `201 { transaction }`.
9. **Client** `handleAddTransaction` resets the form and calls **`fetchAll()`** → GET `/api/finance/transactions` + `/api/finance/budget`.
10. **React** re-renders with the new `transactions` state; `useMemo`s recompute totals/charts/groups; the new row appears.
11. **Dashboard impact:** next time `/dashboard` loads, `getDashboardData` reads the new transaction within its 30-day window and the Finance score/Life Score/brief update.

Every layer is type-checked: Prisma generates TS types from the schema, so a wrong field name fails at compile time.

<a name="14-oauth-flow"></a>
## 14. COMPLETE GOOGLE OAUTH FLOW (with files)

1. **`app/login/page.tsx`** (line 17) — user clicks the button → `signIn("google", { callbackUrl:"/dashboard" })`.
2. **NextAuth** (`app/api/auth/[...nextauth]/route.ts`, GET) builds the Google authorization URL using `GoogleProvider` config from **`lib/auth.ts`** (lines 9–12: `clientId`, `clientSecret`) and redirects the browser to Google.
3. **Google** shows its consent screen; the user authenticates and approves.
4. **Google** redirects back to `/api/auth/callback/google?code=...&state=...` (handled by `app/api/auth/[...nextauth]/route.ts`).
5. **NextAuth** exchanges the `code` + `GOOGLE_CLIENT_SECRET` for Google access/ID tokens (server-to-server; secret never reaches the browser).
6. **PrismaAdapter** (`lib/auth.ts` line 7) upserts a **`User`** row and an **`Account`** row (provider `google`), storing tokens (`prisma/schema.prisma` `Account` model).
7. Because **`session.strategy === "database"`** (`lib/auth.ts` line 15), NextAuth creates a **`Session`** row and sets a `sessionToken` cookie (signed using `NEXTAUTH_SECRET`).
8. The browser is redirected to the `callbackUrl` → **`/dashboard`**.
9. **`app/dashboard/layout.tsx`** (lines 21–22) calls `getServerSession(authOptions)`; the cookie resolves to the `Session`/`User`, so it renders instead of redirecting to `/login`.
10. On every subsequent request, server components and API routes call `getServerSession` to re-verify; "Sign out" (`Sidebar.tsx`) calls `signOut({ callbackUrl:"/login" })`, which deletes the session.
